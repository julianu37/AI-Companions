## O que o run mediu — a maquinaria de colocação

**A colocação não perde nem duplica peça.** O invariante central do plano, medido a cada 25 s pelo amostrador e

| linha final | `peças: 985/985, 0 pulada(s)` + `order ended: hc_ai_blueprint_done` |

**O achado que o run pagou:** os **37** `desistindo de` do run eram **contador mentindo, não peça perdida**. A
barreira de andar, ao estourar a paciência, chamava `SkipPiece` na peça que `PendingBelowIndex` acabara de ler **da
fila do canteiro** - ou seja, uma peça que o canteiro ainda possuía. Cada uma das 37 foi conferida na cena
(`build.pieces`, casamento de pose) e **nenhuma sumiu**: `sumidas de fato: 0`.

O número se denunciava sozinho, e por três caminhos que o `build_run_report.py` fecha na mesma tela:

- a cauda `N pulada(s)` **andou para trás** no log (4 → 3), porque `MarkDone` tira a peça do conjunto de puladas
  quando ela sobe. Um contador monotônico não faz isso;
- o maior `N pulada(s)` do run é **18**, enquanto as linhas `desistindo de` somam **37** - o mesmo evento contado e
  desconado;
- a fala final diz **`985 colocada(s) + 0`**, e é essa a que o jogador ouve.

**Correção (12/11/2026):** o ramo de estouro da paciência em `ServeBarrier` deixou de chamar `SkipPiece`. A peça
continua na fila - e a regra é a que o próprio `AbandonPiece` já escrevia desde 11/11: **peça que nunca foi tentada e
volta pela fila é ADIADA, nunca contada**. Quem realmente descarta a peça (e a conta) é o watchdog de estalo
(`AbandonRetry`). O ramo agora só escreve `LogDebug`; nenhuma peça perdida deixa de ser contada.

> **O DLL do run é o de antes da correção.** `MHR_Build.cs` foi editado às 08:59:44 e a DLL no jogo é de 08:42:55 -
> os 37 são o comportamento antigo, de propósito: este run é a **medição do defeito**, não da correção.
